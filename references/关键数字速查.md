## 1. 最优并行度（实测，非模型推导）

CAID Figure 3（arXiv:2603.21489 §4.2）：

- **Commit0-Lite**：2 → 4 个 engineer 继续提升，**增至 8 反而下降**
- **PaperBench**：超过 2 个后增益极小，runtime 与 cost 持续上升

→ 共享产物的长时程任务，经验甜点 **K=2~4，不要到 8**。
→ 2026-09-26 本仓库自测（§16）把上沿压掉了：同一形状的**写入**扇出上，墙钟净加速的峰值在 **N=2**，N=3 已回落到 1.04。质量甜点与墙钟峰值不是同一个数。
→ 与 USL 的 `N_max=√((1−σ)/κ)` 形状一致（先升后降），这是目前唯一可直接对照的实测曲线。

## 2. 隔离机制消融（CAID Table 3，Claude Sonnet 4.5）

| 配置 | PaperBench | Commit0-Lite |
|---|---|---|
| 单 agent | 57.2 | 53.1 |
| CAID（git worktree 物理隔离） | **63.3** | **59.1** |
| 多 agent 软隔离 | **55.5（低于单 agent）** | 56.1（高于单 agent，低于 worktree）|

软隔离定义（原文）：*"all engineers share one workspace, and the central manager attempts to prevent conflicts through instruction-level constraints, such as assigning non-overlapping files and explicitly warning against interference."*

→ **准确表述**：软隔离并非总是差于单 agent。PaperBench 上更差；Commit0-Lite 上仍优于单 agent，但显著劣于 worktree。
→ 早期二手转述把这条说成"软隔离一律比单 agent 差"，**已按一手论文修正**。

## 3. 并行买的是准确率，不是墙钟时间

CAID Table 2（Claude Sonnet 4.5）：

| 任务 | 单 agent | CAID | 变化 |
|---|---|---|---|
| PaperBench | 1803.5s / cost 3.3 | **2080.4s** / cost 6.5 | **更慢 +15%，贵 2.0×** |
| Commit0-Lite | 692.6s / cost 1.9 | **1583.2s** / cost 8.1 | **慢 2.3×，贵 4.3×** |

论文原话：*"integration remains sequential and test-gated, limiting end-to-end acceleration"*。

→ **需要集成的共享产物任务，并行换的是准确率与吞吐，不是墙钟时间。**
→ 若用户诉求是"更快出结果"，正解是压缩单 agent 路径（减少工具调用、缩小检索范围），而不是加 agent。

## 4. 验证强度权衡（CAID Figure 5）

| 策略 | 通过率 | runtime |
|---|---|---|
| Manager 复核（中心化） | **60.2%** | 3689.1s（最慢）|
| Engineer 自验证（主结果采用） | 55.1% | 2243.9s |
| 效率优先 | 54.0% | 1908.6s（最快）|

→ 中心化复核比自验证高 **5.1 个百分点**，代价 runtime **+64%**。与 Nature MI 的"错误放大 17.2× → 4.4×"方向一致。

## 5. 不要「先单 agent 跑完，再退回多 agent」

CAID Table 2 的 `Single-Agent + CAID` 列：

- PaperBench / Claude：CAID 63.3%（2080.4s / 6.5）→ 单+CAID 66.8%（**3883.9s** / 9.7）
- Commit0-Lite / MiniMax：两者得分**完全相同**（57.0%），后者 runtime 1908.7s → **2660.7s**

→ 长时程共享产物任务：判断后**直接选架构**，不要把"单 agent 跑一遍"当必经步骤。
→ 这与 Step 0「测单 agent 基线」不冲突：**测基线是为了判断，不是为了试错**。

## 6. CAID 论文自陈局限（§6）

- **成本与运行时间**：多 agent 的 API 成本**始终高于**单 agent；wall-clock **未显著减少**（集成是串行且测试门控的）。协调复杂性若不优化，会抵消专业化与并行的收益。
- **委派能力**：中心 manager 的任务分解主要靠 **prompt engineering 启发式**，而非学习到的委派策略；分解过粗或不符合依赖结构时，会产生"局部正确、全局低效"的输出。
- **泛化性**：仅在 SWE 基准上评估（workspace 边界清晰、有版本控制、有可执行测试）。扩展到文档综合、研究规划等非编码领域需重新设计隔离与验证机制。

## 8. 工具并行 vs agent 并行

**子 agent 有固定开销**：业界报告约 **20k tokens/个**（个人技术博客口径，**量级参考、非受控实测**），哪怕它只读一个文件就返回 "LGTM"。任务太轻时，主线程直接做可便宜一个数量级。

**LangChain 多域查询实测**（3 个域 × ~2000 tokens 文档）：

| 模式 | 模型调用 | 总 tokens |
|---|---|---|
| Subagents（隔离）| 5 | **~9K** |
| 单上下文累积 | 3 | ~15K |
| Router | 5 | ~9K |
| Handoffs（串行）| 7+ | ~14K+ |

→ 一次性多域任务：隔离省约 **40%** tokens。
→ **但重复请求时相反**：subagent 无状态，重复请求 8 次调用；有状态模式 5 次（省 40~50%）。
→ **含义**：一次性、多域、大上下文 → 子 agent；重复、轻任务 → 留在主线程。

## 9. 聚合方式与模型配置

**择优 vs 综合**（arXiv:2603.20324, 2026-03, 单作者预印本，N=210 / 42 任务）：

| 配置 | 对单模型基线的胜率 |
|---|---|
| 多样化团队 + **judge 择优** | **0.810** |
| 同质团队（synthesis 聚合）| 0.512（≈随机）|
| Glass's Δ | 2.07 |

- judge-based selection 比 MoA-style synthesis 高 **Δ_WR = +0.631**；42 个任务中 synthesis **在 0 个任务上**被判定优于基线。
- 作者结论：*"selector quality may be a more impactful design lever than generator diversity"*。
- ⚠️ 单作者预印本、未同行评审，"0 of 42" 这一结果异常强，**置信度中等**；方向与 EMNLP 2025 的共识-多样性权衡（集成收益非单调）一致，可交叉佐证。

**模型配置**：

- Anthropic 生产架构：**Opus 4 主 agent + Sonnet 4 子 agent** → +90.2%（orchestrator 强于 worker）。
- CAID：收益在**弱模型**上最大（PaperBench 分模型：MiniMax 2.5 10.5→36.1 = **+25.6**；Claude Sonnet 4.5 57.2→63.3 = **+6.1**）。
- 但 worker 池**内部混用强弱会拖累**：Nature MI 探索性实验，中心化异构团队比强模型同构团队低 **12.6 个百分点**（去中心化异构的 +2.0 主要来自其中较强成员）。
- → 一致建议：**orchestrator 用强模型，worker 池内部同质，worker 可比 orchestrator 弱。**

**相关风险**：模型共享预训练数据 → 错误相关 → Condorcet 陪审团定理的独立性假设不成立。多个 agent 一起自信答错时，多数/共识机制会**放大**错误（有文献称之为 "confabulation consensus"）。⚠️ 该术语与机制来自二手博客转述其引用的 ACL 2025 / EMNLP 2025 论文，**未读原文，置信度中等**。

## 10. 限流 vs 协调成本（两类失败，别混）

| | 协调成本（USL κ）| 限流（429）|
|---|---|---|
| 机理 | 分支互相干扰、合并冲突、契约漂移 | 供应商容量上限 |
| 表现 | 质量下降、返工增多，**不报错** | 显式 429 |
| 建模 | `N_max=√((1−σ)/κ)` | 无公式，需实测探测 |
| 对策 | 降到协调最优 K | AIMD 自适应 |

**有效 K = min(K_协调最优, K_限流上限)。**

AIMD 参数（NVIDIA NeMo Data Designer 生产实现；同类算法见 Envoy / Netflix / GitLab Gitaly / Vector ARC）：

| 参数 | 默认值 | 说明 |
|---|---|---|
| 成功窗口 | 25 次连续成功 | 之后 K **+1**（加性增）|
| 429 降档系数 | **0.75** | 乘性减，快撤 |
| 冷却 | `Retry-After`，缺省 **2s** | |
| 天花板过冲 | **10%** | 回升止于 `天花板 × 1.1`，消除锯齿 |
| 级联抑制 | 仅突发中**第一个** 429 触发 | 否则 5 个并发 429 会让 K 从 20 崩到 4 |

重试（aioresilience 库默认）：指数退避 + jitter，max_attempts 5、initial_delay 1.0s、max_delay 60.0s、multiplier 2.0、jitter 0.1。

## 11. 分解质量、agentic drift 与收益边界

**CooperBench（2026-01，652 任务，Python / TS / Go / Rust）**

- 协作时成功率比单干**低约 50%**；GPT-5 与 Claude Sonnet 4.5 双 agent 协作仅 **25%** 成功
- **增加通信通道带来的改善可忽略**
- 失败构成：Expectation failures **42%**（未更新对伙伴行为的心理模型）> Commitment failures **32%**（承诺了不执行）> Communication breakdown **26%**
- agent 最多把 **20% 行动预算**花在通信上，但缺乏让通信生效的语用理解
- 原话：*"Message passing alone doesn't achieve coordination goals."*

**Agentic drift（并行写入的签名式失败）**

多个 agent 各自独立实现同一概念（不同类名 / 接口 / 假设）→ 代码能编译、测试能过，但代码库里躺着多份冲突实现。
根因：**任务很少真正独立**——软件依赖成网，隔离的 agent 做出局部合理、全局不一致的决策。
→ **测试门控抓不到这类问题**，合并步骤必须额外做重复实现检测；派发时应在契约的全局不变量里写「先查再写」。

**收益边界（实测区间，不是点估计）**

| 来源 | 结果 | 核实状态 |
|---|---|---|
| **CodeCRDT**（Pugachev, arXiv:2510.18893, 2025-10-18，**600 次试验 = 6 任务 × 50 次/模式**）| 部分任务最高 **+21.1% 加速**，另一些最高 **−39.4% 减速**；机制为 CRDT 观察驱动协调 | ✅ **已核对一手摘要，数字一字不差** |
| **Co-Coder**（Yang 等 6 人, arXiv:2606.00953, 2026-05-31，**28 个真实任务**）| pass 率最高 **+14.0%**、墙钟最快 **2.10×**、API 成本最多 **−35%**；对比对象含 file-based 并行基线与 **Claude Code with Agent Teams** | ✅ **已核对一手摘要** |
| arXiv:2410.02506 | 跨 agent 通信使 token 消耗达单链基线 **2×–11.8×** | ⚠️ 未核一手 |
| CooperBench（2026-01，652 任务）| 协作成功率比单干低约 50%；失败构成 Expectation 42% > Commitment 32% > Communication 26% | ⚠️ 未核一手 |

**CodeCRDT 的一条重要旁证**：600 次试验中**零合并失败**，但**语义冲突率仍有 5–10%**。
→ 机械合并干净 ≠ 语义一致。这与 §11 的 agentic drift 相互印证：**测试/合并门控抓不到语义冲突**。

**Co-Coder 的机制**（抽象层）：把多 agent 编排形式化为**图划分问题**，刻画「通信—计算」权衡——分解可缩短关键路径，但跨 agent 依赖需付出上下文传递成本。流程：静态分析建依赖图 → **隔离结构枢纽文件** → 社区发现分区 → 依赖感知调度器执行。**最大收益出现在依赖最密集的项目上。**

**DORA 2025**：AI 采用率 +90% ↔ **bug +9%、代码审查时间 +91%、PR 体积 +154%**（⚠️ 未核一手）。

⚠️ **以下细节仅见于二手汇编，一手摘要未载，引用时须标明未核实**：Co-Coder 的 1.81× 加速下限、28% 成本下限、Infomap 算法名、叶子提升步骤、「近全耦合时退化为串行」这一失败模式；CooperBench 与 2410.02506 的全部数字。

## 12. fit_kappa.py 的选型调研（2026-09-15）

**候选方案六维对比**

| 维度 | PyUSL | sca_tools | scipy 直调 | 自研网格 |
|---|---|---|---|---|
| 功能匹配度 | 中（绑 matplotlib 绘图，CLI 弱）| **高**（CLI + CSV + 置信区间 + 不确定度传播）| 高 | 中（无协方差 → 无区间）|
| License | MIT ✅ | Apache-2.0 ✅ | BSD-3 ✅ | 自研 |
| 维护活跃度 | ❌ 最后提交 **2020-05**，v0.0.4，测试用已废弃的 nose | ❌ **2017**，自述 alpha | ✅ 活跃（本地 1.13.1）| — |
| 安全风险 | 低（matplotlib 属非必要依赖）| 低 | 低 | 低 |
| 代码质量 | 中（0.0.x，测试框架跑不起来）| 中（alpha，但设计完善）| 高 | 中（无 CI）|
| 适配成本 | 低，但引入 matplotlib | 中，需 lmfit，API 未定 | **低** | 0 |

**结论：不依赖任一 USL 库，采用「scipy 为主 + 自研网格兜底」双路径。**

理由：
1. 两个 Python USL 库**均已事实停维护**（2020 / 2017），依赖停维护包比自研更危险——PyUSL 的测试框架 nose 自 2015 年即废弃，测试实际跑不起来。
2. 借鉴它们的成熟做法而非代码：`curve_fit` 做 NLS（PyUSL 与 AnyTune 的共同选择）；**参数不确定度传播**（sca_tools 明确指出的差异化价值）→ 给 N_max 加置信区间。
3. 环境不可假定有 scipy —— **实测：系统 python3 有 scipy 1.13.1，托管 python 3.13.12 没有**。
4. 成熟参考实现在 R：CRAN `usl` 包，含 `peak.scalability` / `optimal.scalability` / `confint` / `overhead` 方法。


> 2026-09-15 那次只回答了"要不要用现成库"。2026-09-26 又查了一次，问的是"怎么测才对"，
> 并且真的据此改了脚本（dof 门槛 5→6、corr(σ,κ)、峰值是否跨过）：见 §17。

**交叉验证结果**：scipy 与自研网格在同一数据上吻合到 4 位有效数字（σ 0.1506 vs 0.1507；κ 0.04991 vs 0.04990）。自研求解器可信。

**实现中修掉的一个隐患**：初版对 4 点完美拟合输出 `N_max=4.13 (95% CI 4.12..4.13)` —— 参数协方差正比于残差方差，合成数据残差近零时区间是人工产物，会给出**虚假精确感**。现按**自由度**设门槛：<5 个观测不给区间（2 参数拟合 4 点 dof=2，残差方差不可估）。

## 13. 曲线形状诊断（借自 Gunther USL 的实践解读）

读拟合曲线形状即可定位病因，**两种形状的对策完全不同**：

| 形状 | 病因 | 对策 |
|---|---|---|
| 趋于平台（Amdahl 型）| **σ 侧**：存在串行部分 | 攻击串行瓶颈本身 |
| **先升后降** | **κ 侧**：共享/协调开销 | **减少共享**（分区、每片独立状态、批量更新），**不是调优并行代码** |

原文要旨：κ 项是 Amdahl 与 Gustafson 都无法表达的——retrograde scaling，即增加并行度反而使吞吐下降，峰值在 `N_max=√((1−σ)/κ)`。

> 本行曾误写为 `N_opt=(1−σ)/κ`（漏了开方）。用 §16 的拟合值即可自证其错：√((1−0.688)/0.064)=**2.20**，而 (1−0.688)/0.064=4.84；把 4.84 代回 C(N) 得 1.000，把 2.20 代回得 1.102，且数值扫描的 argmax 正是 2.20。已改正并在此登记。

**覆盖什么 / 不覆盖什么**

- ❌ 不覆盖：只读扇出（那一行另有自己的两轮 25 臂实测，见 §18——结论是识别不出 κ，所以表里仍写作猜测）、真实仓库的依赖图分片、非编码任务。

- ⚠️ 串行基线由同一 agent 顺序完成，自带学习曲线（后面的单元更快）→ 使加速比**偏高**；反向偏差是每个 agent 的固定开销（实测 96~299s，哪怕只做 1 个单元）→ 使加速比**偏低**。两个方向都出自真实派发，不是调节项。
- ⚠️ 合并耗时含主 agent 的提交与机械求并集解析，不含人工语义裁决；**它本身噪声极大**（N=1 同一套动作：第 1 轮 11.7s、第 2 轮 0.29s；N=2：36.7s vs 0.64s），

- ⚠️ 语料是自建 scratch 仓库：外部效度止于"结构与此同形"的扇出。

## 17. 2026-09-26 的第二次调研：问的是"怎么测"，不是"用什么库"

§12 那次只回答"拟合要不要用现成库"。这一轮要为"把 κ 真量出来"找测法——并发测量有成熟的工业实践，不查就会自己发明一遍错的。

**候选实现与可复用性**（URL 均实际访问）

| 方案 | 许可 | 活动 | 核实状态 | 能否复用 |
|---|---|---|---|---|
| CRAN / R 包 `usl`（`smoeding/usl` 是其镜像）| BSD-2 | 3.0.4，**2025-08-18** | ✅ **DESCRIPTION 一手已亲验** | 唯一在维护的实现，但要 R + nlsr 工具链，塞不进"零网络 stdlib"的技能包 |

**决定：不引依赖，只借语义。** 落到 `scripts/fit_kappa.py` 的三条改动，每条有出处：

1. **κ>0 的唯一证据是回退。** perfdynamics《USL scalability》原文（**已亲验**）：β 项产生 retrograde scaling，必须看到吞吐过峰后下降才谈得上协调成本；同文要求 **"at least half a dozen data points"** → 本项目自由度门槛 **5 → 6**；同文 **"You need to stop measuring and find out why"** → 数据先过有效性门（串行化、时钟）再进拟合。
2. **并排报 corr(σ,κ)。** sca_tools README 的实测样例（7 点 3 变量）报 σ ±32.9%、κ ±19.0%、C(λ,σ) = **0.964**——噪声点上这两个参数几乎分不开。⚠️ 该样例为子 agent 抓取，**未亲验**。本轮 corr = **−0.875**，所以表里的 κ 应读作"σ/κ 这一个合并惩罚的形状"，不是两项独立结论。
3. **三份标量并列：峰值 `√((1−σ)/κ)` 与 κ=0 时的饱和上限 `1/σ`。** R 包另有 `optimal`/`limit` 等方法名。⚠️ 方法名为子 agent 抓取，**未亲验**；`1/σ` 是 Amdahl-only 渐近上限这一条由本地推导 + 数值验证（§16 数据：σ=0.697 → 1.43）。

**测并发时怎么不骗自己（方法论借鉴）**

- **USE 方法**（Brendan Gregg）：利用率 / **饱和度** / 错误分开看。平台自己的并发上限会以队列深度出现 → 本轮把"实际同时运行的 agent 数"做成拒绝门，而不是事后解释。
- **Claim Plane（arXiv:2608.00947）**：静态准入把 **96.7%** 的运行串行化，作者因此**明确撤回墙钟加速结论**。⚠️ 摘要由子 agent 抓取，未亲验。这是"看着在测并行、其实在测调度器"的真实先例。
- **Anthropic 多 agent 工程博客**：agent ≈ 4× chat tokens、多 agent ≈ 15× → 每个 agent 的固定成本必须进分母。⚠️ 未亲验（§7 已引过该源）。
- **k6 / Locust**：预分配 VU 防冷启动污染、到达率模型别让 ramp 冲过头——同一件事的另一说法：**启动成本要计入，且不可当常数**。
- **lmfit 文档**：`nfree = N − Nvarys`；协方差奇异时不给误差棒；**加 bounds 后标准误不可信**。⚠️ 未亲验。→ 本轮 N_max 的 CI 只在 bounds 内采样，当相对宽度读。

**未找到（这也是结论）**：没有任何论文把 USL 的 σ/κ 拟合用在 **LLM agent 团队**上（arXiv 组合检索 0 命中）。§16 的 9 臂因此是**本仓库自证**，不是对某篇文献的复现——引用时按"自有实测、6 档中 3 档复现过"的置信度对待，别写成行业基准。

## 18. 只读档：两轮共 30 臂（轮 2 的 25 臂），仍然不能定 κ —— 而且这次知道为什么了（2026-09-26）

**结论先说（三句）**
1. **那一行没有升格，仍是猜测**，但理由换了：不是"没跑够档"，而是**在这个分片粒度上根本不存在可测的加速**——N=2 到 N=12 每一档的净加速中位数都落在 **0.63~0.83** 之间（没有一个档跑赢串行），档内离散最大 98%，跟档间差同量级。

## 19. 把 §18 换成一个能算的模型：固定开销、扇出尾巴、以及"什么时候才买得到墙钟"（2026-09-27）

§18 交付的是"测不出加速"。本节把同一批数据换成机制模型——**worker 耗时 = 固定开销 a + 每行边际成本 b·行数**，扇出跨度 = K 个耗时里的**最大值**——目的不是把跨度算准，而是把"8~9 到底有没有用"从标签之争变成一个能代进量纲的条件。工具：`ro_model.py`（同目录，`--selftest` 6 支控制）。

**数据面**：把归档臂里的 `shards`（AST 分片时真正发给每个 worker 的文件清单）与 `agent_durations`（worker 自报 `t_end − t_start`）逐一对齐；**长度不匹配的臂整条丢弃并打印文件名**，本次 0 条被丢。**40 个 worker 观测，来自 13 个臂**（小+大语料；mid 的 50 个观测按 §20 的设计只作打分，不进拟合）。**旧版这里写的是「76 个观测 / 14 个归档臂」，那是重复计数**：每臂在 collect 与 row 各存一份档案，两份都被读进拟合，见 §21。另外被编排器括号救回的臂没有 per-worker 时钟，因此不进拟合——这是本节的取样偏差，宽档的可靠性成本只算进了 §18 的分母，没算进这里的 a。

**结果二（本节真正的头条）：起作用的是"总工作量 ÷ 有效并发"，不是"每片几个文件"。** 我先前把这一步归因给每片厚度（3~5 个文件），**K=18 那一臂把它证伪了**：同一份 mid 语料、**每片只有 2 个文件**、17 个 worker 同时在跑，跨度 211.7 秒 vs 串行 347.2 秒 ⇒ **1.64×**（该臂作为"18 路"的证据被并发门拒绝，但"每片 2 个文件也能买到墙钟"这件事，17 路并发就足以说明）。对照小语料：每片 1~2 个文件、串行只有 78~165 秒时，**22 个臂一个都没过 1.0**。两组的差别在**总量**，不在每片文件数 ⇒ 上一版的"每片 ≥3~5 个文件"已改为行内更正，不留作结论。

**新增的第三种通道故障（派发内容丢失）**：K=8 的第三次尝试里，3 号 worker 收到的派发消息**是空的**（没有 brief 路径）。它自己推理恢复：查 `arm.json` 的 dispatch 时刻、找出唯一未落地的结果文件名、读对应的 brief ⇒ 分片**恰好与装置派发的一致**（我事后逐字节核对：dealt 5 = reported 5，无差集），census 36/36 判分通过；**但它的 t_start 比派发消息晚 313 秒**，于是编排器只观测到 **7/8 并发** ⇒ 该臂被 §18 的并发门拒绝记账（拒绝，不夹平）。三条教训：① **worker 的自愈推理可以产出"看起来正确"的臂，但时间轴已经不可信**——判分能过不代表这臂可记账；② 它主动写下"不要把我的 t_start 送进 min(t_start)"，这是自报边界的范例，装置应欢迎而不是回避；③ **派发失败有三种形态**：worker 整条丢（K=12）、并发数被平台截断（K=18→17）、载荷丢失而 worker 自愈（本次），只有第一种是我原先想到的。**复算入口**：`RO_SERIES=mid python3 ro_measure.py levels`、`python3 ro_model.py`（out-of-sample 段：`fitted on 76 durations from small+big (mid's N durations excluded by design)` + 逐档 threshold/constructive 两种形式的 pred-obs）；原始行 `parallel-log-readonly-mid.csv`（**7 条记账臂**），被拒臂的归档在 `roarms-mid/ro_arm_N18_collect.json`（`concurrency_observed=17`），重派隔离件 `../kappa-rework-mid/run-20260927-010657/`。

## 21. 审计自己那把尺子：重复计数、互相覆盖的归档、以及"控制读的集合和报告不是同一个"（2026-09-27）

跑复现批次时顺手核了核装置，抓出四个**仪表侧**缺陷。它们都不影响"符号检验"和"门槛式被证伪"这两条结论（那两条来自 CSV 记账行与并发门），但影响 §19 引用的常数与样本量：

1. **重复计数（影响 a/b/R² 与所有样本量）**：每臂在 collect 时归档一份、row 时再归档一份，`observations()` 把两份都读进拟合 ⇒ 样本量虚高近一倍（**76 → 40**），两份**并不相同**（返工合并会改 agent 列表），所以重复不是等权复制。修好后：a 50.3 → **47.0 秒**、b 0.118 → **0.142 s/行**、R² 0.323 → **0.376**、σ 0.41 → **0.42**；样本 76 → **40 行 / 8 个臂**。**但小语料单独的拟合（a=55.6、b=0.0804、R²=0.2416）去重前后一字不差**——把每行原样复制两份不改变 OLS，这一点我实测过。因此变化的来源不是"重复"本身，而是**两个缺陷叠加**：归档按并发度命名会被后一轮覆写，于是"final 集"与"snapshot 集"里装着**不同轮次的臂**，旧代码把 14 个文件当成 14 个臂，实际是 7 个 final + 7 个快照、且两两不属于同一臂。这条只能记在这里，历史归档无法还原。
2. **归档按并发度命名 ⇒ 跨轮互相覆盖**：`ro_arm_N8.json` 被每一轮 K=8 的臂覆写，所以"25 臂实测"在归档里只剩 7 个臂的 final（+7 个 collect 快照）。记账行（CSV）是安全的，**per-worker 观测不是**。已改为按 dispatch 时刻命名（`ro_arm_N8-1790447666.json`），历史损失无法追回，如实记在这里。
3. **自测与报告读的不是同一个集合**：`--selftest` 在"全部观测"上拟合，报告在"只用 small+big"上拟合。当 mid 加进来后，自测打出的 a 一度是 88.7（含 mid 的合并拟合），而报告是 47.0 —— **一支断言"a 在几十秒量级"的控制，验的却是另一份数据**。已让自测走同一个 `FIT_SERIES` 过滤器，并让它**自报口径**（`selftest now fits on FIT_SERIES only (40 of 90 rows)`）。
4. **静默跳过 = 与"没有"同形**：`read_log()` 对不存在的日志文件直接跳过，`observations()` 曾经对 shards/耗时数量不匹配的臂静默丢弃。前者已改成打 WARNING；后者本轮在 mid 的 K=12 臂上真实触发（12 shards vs 11 durations ⇒ 整臂丢弃并打印），这正是"配对不上就丢，不猜偏移"该有的表现。

**独立复核**：恢复被我自己的 splice 削掉的 `ols()`/`lognormal_max_factor()` 时，用 scipy 的 `linregress` 对同一批 40 行独立重算，三个数逐位吻合（a 46.971 / b 0.14201 / R² 0.3759）；`lognormal_max_factor` 按 K=2 给 1.36、K=1 给 1.0 复算一致。**被这次 splice 波及的只有 ro_model.py 的两个 helper**（文件其余函数逐个 grep 核过），数据文件未被写入。

把每一次读数拆成恒等式 `measured = denom × ideal × loss`（乘积必须等于读数，自测里钉住）：

    denom = 本轮串行读数 / (a + b·L)        分母抽到哪一档
    ideal = (a + b·L) / (a + b·L/N)         纯分片的天花板，构造上 < N
    loss  = (a + b·L/N) / 实测跨度          尾巴 + 通道

pin N=4 那支 4.285 于是拆成 **1.49 × 3.00 × 0.96 = 4.285**：`ideal=3.00 < N=4` 说明**分片本身永远买不到超线性**（每条 worker 都要重付一次 a），超线性全部来自 `denom=1.49`（这一轮的串行臂比它自己那个 worker 模型慢 49%），而 `loss=0.96` 说明这一支跨度已经贴着模型每片成本、**几乎没有尾巴**。11 支可拆的臂里 `denom` 中位 1.27（范围 0.72~1.49）、`ideal` 中位 1.89（1.46~3.00）、`loss` 中位 0.84（0.36~1.21）。

四条能落笔的结论：

1. **A 的整条区间 [0, 0.177] 都是"零干扰"能给出的读数**。也就是说，如果在这条通道上拟合出 κ̂=0.05，那**不构成任何证据**；要越过这条地板，κ̂ 得大于 **0.24**（㉓ 起由 `ro_face_sync.py` 的 bar-band 段现写，带与八读数、两把模型各自的线见 ㉓ 那段，不在此复抄；0.19 / 0.21 / 0.20 / 0.23 / 0.29 五版都已作废）（本句原写 0.155，已被 ⑯ 的重算取代）（0.1442 是本建模 seed 7 那一路的上沿；同 reps 换 seed 与换建模会把它推到 **0.1506**，整袋版 seed 7 是 0.1421 ⇒ 这条线是**实测带之上留出的余量**，不是某个精确上沿，四位小数是假的）。每档加到 5 支，上沿也只从 0.1442 收到 0.1186。（§16 那个写入档 κ̂=**0.069** 就落在这条带里——但本表原料全部来自只读装置，**写入档没量过 cov**，所以对 §16 只能算"待复算的怀疑"，不是已证伪，见下"未证实"。）
2. **多加重复不是杠杆**：每档从 1 支加到 5 支，A 的 κ̂ 中位几乎不动（0.0464→0.0440）、上沿只从 0.1442 收到 0.1186。因为自助的是每档自己的分布，中位数收敛到的正是那条**被队列扭曲的期望曲线**。
3. **谁贡献了偏差被分开了，但不是我原先说的那种分法**：把交付修成完美（A→B）κ̂ 中位 0.0464→0.0251、上沿 0.1442→0.0501（**收 65%**）；而把 2.55 倍的分母冻结成一个常数（A→C）只收到 0.0345 / 0.1213（**收 16%**），而且在完美交付那一侧方向还反过来（B→D：0.0251→0.0307）。**主项是交付；但"分母只平移水平、完全不碰曲率"这句我上一版说过头了**——在一个**没有 N=1 锚点**的拟合里（我们的记账行只到 N≥2 的臂，N=1 是分母不是点），把整条曲线乘一个常数会被 σ/κ 部分吸收，所以分母的水平误差也会漏进曲率，只是量级比交付小。这正好说明"逐轮配对分母"为什么必要而不充分——它救的是 level，不是 κ。
4. **即使通道完美也有一块地板**：D 给 κ̂≈**0.021**、N_max≈**6.8**，纯粹来自"跨度 = N 个独立时长里的最大值"这一件事（每档残差 sd 10~22 秒）。所以**"N_max≈7"是这类任务形状在零干扰下的签名**，不是发现；但 D 的退行率只有 0~1%，即拟合器自己那条"没看见退行就判不可辨识"的门在完美通道上基本不冤枉人——**A 里 30~39% 的假退行是通道造出来的**。

限制写在这里：残差自助把宽档争用（sd 从 N=4 的 11 秒涨到 N=12 的 20 秒）**折进了 job 时长**而不是 κ，所以 A 的地板是**下界**；每档 cov/N 的实测样本只有 1~6 支，区间继承了这份单薄；分母有 4 个抽样。这三条要靠**多投臂**才能收窄，与结论 2 不矛盾——结论 2 说的是多投臂不解决**通道**。**残差建模敏感性 + 蒙特卡洛散布**（`--residuals pooled --reps 1000`，同样的四次分母，seed 7/11/23）：整袋版 A 的上沿 **0.1421 / 0.1339 / 0.1351**，逐档版 **0.1442 / 0.1382 / 0.1506** ⇒ 六次读数合起来是一条 **0.134~0.151** 的带。我上一版在这里写的是「整袋上沿 0.1547、两版差 7%」，那是拿 `--reps 1000` 的逐档版与 `--reps 400` 的整袋版并排比出来的——**那 7% 大部分是 400 次的蒙特卡洛噪声，不是建模敏感性**：对齐 reps 之后，建模之间的差（1.5%）**小于**换 seed 的差（最大 0.012）。中位照旧不稳健：0.0464 → **0.0164**（差 2.8 倍）。所以地板仍按**上沿**判，而 **判据线现为 0.24**（㊲ 重放；㉙ 那版旧值 0.25）（㉓，由 ㉓ 的 bar-band 段现写，带与八读数不在此复抄；⑲ 曾把 0.21 作废、⑳ 按同一条规则算了回去、㉒ 又落回 0.20、㉓ 抬到 0.23、㉖ 抬到 0.29、㉙ 因 draw 13 的三支同窗口臂与第 10 条分母落回 0.25——派生值不设永久作废；「0.155 = 带 0.134~0.151 之上的余量」这一版也被 ⑯ 的重算取代），不是「两版取 max」；上沿本身不许再当四位数引用。两版都不影响结论 1：§16 的 0.069 落在带内。

三条结论：
1. **κ 的发表值优先出自 scipy**；grid 是 40 格步长的网格搜索，**它的分辨率下限就是它自己的格点**——连无噪真零都恢复不到 0，只是这次误差 0.0032 还没到"能编故事"的量级。
2. **两个求解器都会凭空造 κ**：真 κ=0 的饱和曲线加 25% 噪声后，grid 有 30%、scipy 有 24% 的重跑把 κ 报成 >0.02。⇒ 这不再只是"我们这条通道实测噪声大"的推断，而是**真值已知时的直接测量**：单次拟合出一个正的 κ，本身就不构成证据；要证据得看**有没有跨越峰值的倒退尾巴**，不是看求解器。
3. 因此 §19（scipy）与地板/敏感性（grid）**混用是有代价的**，代价现在有了数字：同一 5 点差 κ 一倍（0.020 vs 0.040）。引用规则：**σ/κ 与 N_max 必须连求解器一起写，跨求解器不可比；要判"有没有 κ"用地板线，不用任何单一求解器的点估计。**

先记两件在派发**之前**撞出来的仪表缺陷，因为它们都属于"闸门看着在判、其实没判"这一类：

1. **门槛的边界被浮点吃掉了。** 记账面上 `cov` 只存两位小数，draw 8 那支写的是 `cov=2.40/3`，解析回来是 `0.7999999999999999`，于是 `cov_n < 0.8` 成立——**一支面上印着"0.80"的臂被 ≥0.80 的门槛拒了**，而输出行同时印着 `below threshold excluded [... pin/8@N=3(0.80)]`，一句话里自相矛盾。修法是让比较的精度与存面的精度一致（`COV_EPS = 1e-9`），并且配两支反向控制：面上正好落在门槛上的臂必须留在拟合里，而 `0.795` 这种真不够的仍要被挡（否则 epsilon 就成了免检）。
