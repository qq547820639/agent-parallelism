# 关键数字速查

改动 `SKILL.md` 时以本表为准。所有数字附来源与边界，**引用时不可脱离口径**。

## 1. 最优并行度（实测，非模型推导）

CAID Figure 3（arXiv:2603.21489 §4.2）：

- **Commit0-Lite**：2 → 4 个 engineer 继续提升，**增至 8 反而下降**
- **PaperBench**：超过 2 个后增益极小，runtime 与 cost 持续上升

→ 共享产物的长时程任务，经验甜点 **K=2~4，不要到 8**。
→ 2026-09-26 本仓库自测（§16）把上沿压掉了：同一形状的**写入**扇出上，墙钟净加速的峰值在 **N=2**，N=3 已回落到 1.04。质量甜点与墙钟峰值不是同一个数。
→ 与 USL 的 `N_max=√((1−σ)/κ)` 形状一致（先升后降），这是目前唯一可直接对照的实测曲线。

## 2. 隔离机制消融（CAID Table 3，Claude Sonnet 4.5）

| 配置 | PaperBench | Commit0-Lite |
|---|---|---|
| 单 agent | 57.2 | 53.1 |
| CAID（git worktree 物理隔离） | **63.3** | **59.1** |
| 多 agent 软隔离 | **55.5（低于单 agent）** | 56.1（高于单 agent，低于 worktree）|

软隔离定义（原文）：*"all engineers share one workspace, and the central manager attempts to prevent conflicts through instruction-level constraints, such as assigning non-overlapping files and explicitly warning against interference."*

→ **准确表述**：软隔离并非总是差于单 agent。PaperBench 上更差；Commit0-Lite 上仍优于单 agent，但显著劣于 worktree。
→ 早期二手转述把这条说成"软隔离一律比单 agent 差"，**已按一手论文修正**。

## 3. 并行买的是准确率，不是墙钟时间

CAID Table 2（Claude Sonnet 4.5）：

| 任务 | 单 agent | CAID | 变化 |
|---|---|---|---|
| PaperBench | 1803.5s / cost 3.3 | **2080.4s** / cost 6.5 | **更慢 +15%，贵 2.0×** |
| Commit0-Lite | 692.6s / cost 1.9 | **1583.2s** / cost 8.1 | **慢 2.3×，贵 4.3×** |

论文原话：*"integration remains sequential and test-gated, limiting end-to-end acceleration"*。

→ **需要集成的共享产物任务，并行换的是准确率与吞吐，不是墙钟时间。**
→ 若用户诉求是"更快出结果"，正解是压缩单 agent 路径（减少工具调用、缩小检索范围），而不是加 agent。

## 4. 验证强度权衡（CAID Figure 5）

| 策略 | 通过率 | runtime |
|---|---|---|
| Manager 复核（中心化） | **60.2%** | 3689.1s（最慢）|
| Engineer 自验证（主结果采用） | 55.1% | 2243.9s |
| 效率优先 | 54.0% | 1908.6s（最快）|

→ 中心化复核比自验证高 **5.1 个百分点**，代价 runtime **+64%**。与 Nature MI 的"错误放大 17.2× → 4.4×"方向一致。

## 5. 不要「先单 agent 跑完，再退回多 agent」

CAID Table 2 的 `Single-Agent + CAID` 列：

- PaperBench / Claude：CAID 63.3%（2080.4s / 6.5）→ 单+CAID 66.8%（**3883.9s** / 9.7）
- Commit0-Lite / MiniMax：两者得分**完全相同**（57.0%），后者 runtime 1908.7s → **2660.7s**

→ 长时程共享产物任务：判断后**直接选架构**，不要把"单 agent 跑一遍"当必经步骤。
→ 这与 Step 0「测单 agent 基线」不冲突：**测基线是为了判断，不是为了试错**。

## 6. CAID 论文自陈局限（§6）

- **成本与运行时间**：多 agent 的 API 成本**始终高于**单 agent；wall-clock **未显著减少**（集成是串行且测试门控的）。协调复杂性若不优化，会抵消专业化与并行的收益。
- **委派能力**：中心 manager 的任务分解主要靠 **prompt engineering 启发式**，而非学习到的委派策略；分解过粗或不符合依赖结构时，会产生"局部正确、全局低效"的输出。
- **泛化性**：仅在 SWE 基准上评估（workspace 边界清晰、有版本控制、有可执行测试）。扩展到文档综合、研究规划等非编码领域需重新设计隔离与验证机制。

## 8. 工具并行 vs agent 并行

**子 agent 有固定开销**：业界报告约 **20k tokens/个**（个人技术博客口径，**量级参考、非受控实测**），哪怕它只读一个文件就返回 "LGTM"。任务太轻时，主线程直接做可便宜一个数量级。

**LangChain 多域查询实测**（3 个域 × ~2000 tokens 文档）：

| 模式 | 模型调用 | 总 tokens |
|---|---|---|
| Subagents（隔离）| 5 | **~9K** |
| 单上下文累积 | 3 | ~15K |
| Router | 5 | ~9K |
| Handoffs（串行）| 7+ | ~14K+ |

→ 一次性多域任务：隔离省约 **40%** tokens。
→ **但重复请求时相反**：subagent 无状态，重复请求 8 次调用；有状态模式 5 次（省 40~50%）。
→ **含义**：一次性、多域、大上下文 → 子 agent；重复、轻任务 → 留在主线程。

## 9. 聚合方式与模型配置

**择优 vs 综合**（arXiv:2603.20324, 2026-03, 单作者预印本，N=210 / 42 任务）：

| 配置 | 对单模型基线的胜率 |
|---|---|
| 多样化团队 + **judge 择优** | **0.810** |
| 同质团队（synthesis 聚合）| 0.512（≈随机）|
| Glass's Δ | 2.07 |

- judge-based selection 比 MoA-style synthesis 高 **Δ_WR = +0.631**；42 个任务中 synthesis **在 0 个任务上**被判定优于基线。
- 作者结论：*"selector quality may be a more impactful design lever than generator diversity"*。
- ⚠️ 单作者预印本、未同行评审，"0 of 42" 这一结果异常强，**置信度中等**；方向与 EMNLP 2025 的共识-多样性权衡（集成收益非单调）一致，可交叉佐证。

**模型配置**：

- Anthropic 生产架构：**Opus 4 主 agent + Sonnet 4 子 agent** → +90.2%（orchestrator 强于 worker）。
- CAID：收益在**弱模型**上最大（PaperBench 分模型：MiniMax 2.5 10.5→36.1 = **+25.6**；Claude Sonnet 4.5 57.2→63.3 = **+6.1**）。
- 但 worker 池**内部混用强弱会拖累**：Nature MI 探索性实验，中心化异构团队比强模型同构团队低 **12.6 个百分点**（去中心化异构的 +2.0 主要来自其中较强成员）。
- → 一致建议：**orchestrator 用强模型，worker 池内部同质，worker 可比 orchestrator 弱。**

**相关风险**：模型共享预训练数据 → 错误相关 → Condorcet 陪审团定理的独立性假设不成立。多个 agent 一起自信答错时，多数/共识机制会**放大**错误（有文献称之为 "confabulation consensus"）。⚠️ 该术语与机制来自二手博客转述其引用的 ACL 2025 / EMNLP 2025 论文，**未读原文，置信度中等**。

## 10. 限流 vs 协调成本（两类失败，别混）

| | 协调成本（USL κ）| 限流（429）|
|---|---|---|
| 机理 | 分支互相干扰、合并冲突、契约漂移 | 供应商容量上限 |
| 表现 | 质量下降、返工增多，**不报错** | 显式 429 |
| 建模 | `N_max=√((1−σ)/κ)` | 无公式，需实测探测 |
| 对策 | 降到协调最优 K | AIMD 自适应 |

**有效 K = min(K_协调最优, K_限流上限)。**

AIMD 参数（NVIDIA NeMo Data Designer 生产实现；同类算法见 Envoy / Netflix / GitLab Gitaly / Vector ARC）：

| 参数 | 默认值 | 说明 |
|---|---|---|
| 成功窗口 | 25 次连续成功 | 之后 K **+1**（加性增）|
| 429 降档系数 | **0.75** | 乘性减，快撤 |
| 冷却 | `Retry-After`，缺省 **2s** | |
| 天花板过冲 | **10%** | 回升止于 `天花板 × 1.1`，消除锯齿 |
| 级联抑制 | 仅突发中**第一个** 429 触发 | 否则 5 个并发 429 会让 K 从 20 崩到 4 |

重试（aioresilience 库默认）：指数退避 + jitter，max_attempts 5、initial_delay 1.0s、max_delay 60.0s、multiplier 2.0、jitter 0.1。

## 11. 分解质量、agentic drift 与收益边界

**CooperBench（2026-01，652 任务，Python / TS / Go / Rust）**

- 协作时成功率比单干**低约 50%**；GPT-5 与 Claude Sonnet 4.5 双 agent 协作仅 **25%** 成功
- **增加通信通道带来的改善可忽略**
- 失败构成：Expectation failures **42%**（未更新对伙伴行为的心理模型）> Commitment failures **32%**（承诺了不执行）> Communication breakdown **26%**
- agent 最多把 **20% 行动预算**花在通信上，但缺乏让通信生效的语用理解
- 原话：*"Message passing alone doesn't achieve coordination goals."*

**Agentic drift（并行写入的签名式失败）**

多个 agent 各自独立实现同一概念（不同类名 / 接口 / 假设）→ 代码能编译、测试能过，但代码库里躺着多份冲突实现。
根因：**任务很少真正独立**——软件依赖成网，隔离的 agent 做出局部合理、全局不一致的决策。
→ **测试门控抓不到这类问题**，合并步骤必须额外做重复实现检测；派发时应在契约的全局不变量里写「先查再写」。

**收益边界（实测区间，不是点估计）**

| 来源 | 结果 |
|---|---|
| 来源 | 结果 | 核实状态 |
|---|---|---|
| **CodeCRDT**（Pugachev, arXiv:2510.18893, 2025-10-18，**600 次试验 = 6 任务 × 50 次/模式**）| 部分任务最高 **+21.1% 加速**，另一些最高 **−39.4% 减速**；机制为 CRDT 观察驱动协调 | ✅ **已核对一手摘要，数字一字不差** |
| **Co-Coder**（Yang 等 6 人, arXiv:2606.00953, 2026-05-31，**28 个真实任务**）| pass 率最高 **+14.0%**、墙钟最快 **2.10×**、API 成本最多 **−35%**；对比对象含 file-based 并行基线与 **Claude Code with Agent Teams** | ✅ **已核对一手摘要** |
| arXiv:2410.02506 | 跨 agent 通信使 token 消耗达单链基线 **2×–11.8×** | ⚠️ 未核一手 |
| CooperBench（2026-01，652 任务）| 协作成功率比单干低约 50%；失败构成 Expectation 42% > Commitment 32% > Communication 26% | ⚠️ 未核一手 |

**CodeCRDT 的一条重要旁证**：600 次试验中**零合并失败**，但**语义冲突率仍有 5–10%**。
→ 机械合并干净 ≠ 语义一致。这与 §11 的 agentic drift 相互印证：**测试/合并门控抓不到语义冲突**。

**Co-Coder 的机制**（抽象层）：把多 agent 编排形式化为**图划分问题**，刻画「通信—计算」权衡——分解可缩短关键路径，但跨 agent 依赖需付出上下文传递成本。流程：静态分析建依赖图 → **隔离结构枢纽文件** → 社区发现分区 → 依赖感知调度器执行。**最大收益出现在依赖最密集的项目上。**

**DORA 2025**：AI 采用率 +90% ↔ **bug +9%、代码审查时间 +91%、PR 体积 +154%**（⚠️ 未核一手）。

⚠️ **以下细节仅见于二手汇编，一手摘要未载，引用时须标明未核实**：Co-Coder 的 1.81× 加速下限、28% 成本下限、Infomap 算法名、叶子提升步骤、「近全耦合时退化为串行」这一失败模式；CooperBench 与 2410.02506 的全部数字。

## 12. fit_kappa.py 的选型调研（2026-09-15）

**候选方案六维对比**

| 维度 | PyUSL | sca_tools | scipy 直调 | 自研网格 |
|---|---|---|---|---|
| 功能匹配度 | 中（绑 matplotlib 绘图，CLI 弱）| **高**（CLI + CSV + 置信区间 + 不确定度传播）| 高 | 中（无协方差 → 无区间）|
| License | MIT ✅ | Apache-2.0 ✅ | BSD-3 ✅ | 自研 |
| 维护活跃度 | ❌ 最后提交 **2020-05**，v0.0.4，测试用已废弃的 nose | ❌ **2017**，自述 alpha | ✅ 活跃（本地 1.13.1）| — |
| 安全风险 | 低（matplotlib 属非必要依赖）| 低 | 低 | 低 |
| 代码质量 | 中（0.0.x，测试框架跑不起来）| 中（alpha，但设计完善）| 高 | 中（无 CI）|
| 适配成本 | 低，但引入 matplotlib | 中，需 lmfit，API 未定 | **低** | 0 |

**结论：不依赖任一 USL 库，采用「scipy 为主 + 自研网格兜底」双路径。**

理由：
1. 两个 Python USL 库**均已事实停维护**（2020 / 2017），依赖停维护包比自研更危险——PyUSL 的测试框架 nose 自 2015 年即废弃，测试实际跑不起来。
2. 借鉴它们的成熟做法而非代码：`curve_fit` 做 NLS（PyUSL 与 AnyTune 的共同选择）；**参数不确定度传播**（sca_tools 明确指出的差异化价值）→ 给 N_max 加置信区间。
3. 环境不可假定有 scipy —— **实测：系统 python3 有 scipy 1.13.1，托管 python 3.13.12 没有**。
4. 成熟参考实现在 R：CRAN `usl` 包，含 `peak.scalability` / `optimal.scalability` / `confint` / `overhead` 方法。

**交叉验证结果**：scipy 与自研网格在同一数据上吻合到 4 位有效数字（σ 0.1506 vs 0.1507；κ 0.04991 vs 0.04990）。自研求解器可信。

**实现中修掉的一个隐患**：初版对 4 点完美拟合输出 `N_max=4.13 (95% CI 4.12..4.13)` —— 参数协方差正比于残差方差，合成数据残差近零时区间是人工产物，会给出**虚假精确感**。现按**自由度**设门槛：<5 个观测不给区间（2 参数拟合 4 点 dof=2，残差方差不可估）。

## 13. 曲线形状诊断（借自 Gunther USL 的实践解读）

读拟合曲线形状即可定位病因，**两种形状的对策完全不同**：

| 形状 | 病因 | 对策 |
|---|---|---|
| 趋于平台（Amdahl 型）| **σ 侧**：存在串行部分 | 攻击串行瓶颈本身 |
| **先升后降** | **κ 侧**：共享/协调开销 | **减少共享**（分区、每片独立状态、批量更新），**不是调优并行代码** |

原文要旨：κ 项是 Amdahl 与 Gustafson 都无法表达的——retrograde scaling，即增加并行度反而使吞吐下降，峰值在 `N_max=√((1−σ)/κ)`。

> 本行曾误写为 `N_opt=(1−σ)/κ`（漏了开方）。用 §16 的拟合值即可自证其错：√((1−0.688)/0.064)=**2.20**，而 (1−0.688)/0.064=4.84；把 4.84 代回 C(N) 得 1.000，把 2.20 代回得 1.102，且数值扫描的 argmax 正是 2.20。已改正并在此登记。

## 16. σ / κ 的首次实测（2026-09-26，本仓库自己做的）

**读数（9 臂 / 6 档 / 两轮）**：写入 / 共享状态型 agent 扇出 —— **σ=0.697、κ=0.069、N_max=2.09（95% CI 1.64~2.49）、R²=0.692、corr(σ,κ)=−0.875、1/σ=1.43**，建议 **K=2**。
只取第 1 轮 6 臂时是 σ=0.688 / κ=0.064 / N_max=2.20 / R²=0.833——**结论（K=2）不变，但单轮的 R² 明显偏乐观**：复现后 SSE 从 0.0206 涨到 0.0531。

**装置**（一次性 scratch 仓库，不在技能目录内）：12 个**互不相同**的单元（popcount、next prime、8 位反转、Gray 码、aliquot sum…——每个都要独立想，防止"一个模板套 12 份"让总工作量失真）+ 1 个**共享**索引文件（所有分片改同一行 → 冲突是结构性的，不是偶发）。每片一个 git worktree、一个独立 agent；主 agent 提交并合并；**验收由独立参考实现逐点比对**（x∈0..64）+ 注册不变量 + 重复实现检测，不接受子 agent 自报绿。

**原始观测**（speedup = 串行 ÷（并行 + 合并 + 返工）；串行基线 = 同一个 agent 顺序做完 12 个单元 = 299.0s）：

| N | 每片单元数 | 并行墙钟 s | 合并 s | 冲突数 | 净加速 |
|---|---|---|---|---|---|
| 1 | 12 | 299.0 | 11.7 | 0 | 0.962 |
| 2 | 6 | 209.7 | 36.7 | 1 | **1.214** |
| 3 | 4 | 228.8 | 59.5 | 2 | 1.037 |
| 4 | 3 | 246.0 | 57.5 | 3 | 0.985 |
| 6 | 2 | 259.1 | 55.9 | 5 | 0.949 |
| 12 | 1 | 299.8 | 111.7 | 11 | 0.727 |
| 1 | 12 | 348.6 | 0.3 | 0 | 0.999 | ← 第 2 轮
| 2 | 6 | 296.6 | 0.6 | 1 | 1.173 | ← 第 2 轮
| 4 | 3 | 401.3 | 0.4 | 3 | 0.868 | ← 第 2 轮 |

第 2 轮各行除以**本轮**串行基线 348.6s。峰值两轮都在 **N=2**、其后回落（retrograde）——就是这一行使 κ 可辨识；扫描若只到上升段，脚本会直接判 "kappa NOT identifiable"。

**覆盖什么 / 不覆盖什么**
- ✅ 覆盖：多个 agent 各写一片、必须合并回同一份产物的**写入 / 共享状态**任务。
- ❌ 不覆盖：只读扇出（表里 κ=0.01 那行仍是猜测）、真实仓库的依赖图分片、非编码任务。
- ⚠️ **只有 3 个档复现过（N=1/2/4）**，其余仍是单点。同档同范围的两个 agent 用时能差 3.1×（N=12 那轮 96~299s），单点噪声量级与参数差同量级；corr=−0.875 也说明 6 个档上 σ 与 κ 分得不干净。**把 N_max 读成"2 附近"，别读成"2.09"**。
- ⚠️ 串行基线由同一 agent 顺序完成，自带学习曲线（后面的单元更快）→ 使加速比**偏高**；反向偏差是每个 agent 的固定开销（实测 96~299s，哪怕只做 1 个单元）→ 使加速比**偏低**。两个方向都出自真实派发，不是调节项。
- ⚠️ 合并耗时含主 agent 的提交与机械求并集解析，不含人工语义裁决；**它本身噪声极大**（N=1 同一套动作：第 1 轮 11.7s、第 2 轮 0.29s；N=2：36.7s vs 0.64s），
     说明这段时间主要是卷/git 的暖机开销，不是协调成本。**随 N 稳定增长的是冲突数（0/1/2/3/5/11），不是合并秒数**——论证 κ 时该引冲突数与回落形状。
- ⚠️ 语料是自建 scratch 仓库：外部效度止于"结构与此同形"的扇出。

**一次会被静默吞进拟合的读数事故**：第 2 轮首个 N=4 臂里，一个子 agent 的 `date` 时钟比主机慢 **3.17e6 秒**，自报区间 36.7 天。它自己发现并警告"别把这个喂给拟合"。危险在于：`parallel_seconds = max(t_end) - min(t_start)`，一个被污染的端点**就成了整臂的墙钟**，而并发门看不见它（那条假区间和谁都重叠），速度会算成 ≈0.0001 并被当成真实观测写进曲线。修法不是把数钳回来，而是**拒绝记行**：`arm.py` 增加时钟门（t_start 不得早于编排侧 t_prep−30s、区间不得超过本轮串行基线的 3×、非正长度即异常），并把**这条真实异常原样留成必开火控制**（`arm.py clock-test` 的 K2）。该臂作废后重新派发了一轮干净的 N=4。

**过程中两次真实的协调失败（都是"各自全绿、合并后红"）**
1. 分片 1 用单引号写 `FEATURE_MODULES = ['f1','f5','f9']`，fan-in 脚本只认双引号 → 3 个登记被静默吞掉。
2. 分片 2 不动列表字面量、改写 `FEATURE_MODULES.append("f2")` → 同样被吞。

两次都是各分片 pytest 全绿、合并后才由 `test_every_implemented_module_is_registered` 报红。→ Step 3 的 4.4× vs 17.2× 不是仪式：本轮以"每个实现者都自证通过、主线 3 个单元未登记"的形式复现了一次。修法是**派生件原则**：索引按磁盘上真实存在的单元重算；同时把"提到却无文件"的幻影登记单独报出，不静默处理。

**装置不在本仓库内**：本仓库根目录即技能本体，而技能按上下文预算装载，不该塞进一套 benchmark 装置。它落在 `/Volumes/Extra/CodeProj/kappa-measure/`（**机器本地路径，非仓库内容**）。该目录若已不在，按本节口径重建即可——三条硬读数（κ=0 上限 1/σ、corr(σ,κ)、峰值是否跨过）已在 `scripts/fit_kappa.py` 里实现并有自测控制，缺的只是派发装置。

**重跑方式**（在测量目录内）：`arm.py prep N` → 派 N 个 agent 各读自己的 brief → `arm.py close` / `merge` / `verify` → `arm.py row`。三道拒绝门：观测到的并发数 < N（平台静默串行化，此臂作废）、臂未变绿且未记返工、同一臂重复记行。校验器带 9 个必开火控制 + 8 个 fan-in 控制，全绿才允许产出读数。
