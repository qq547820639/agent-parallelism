# Agent Parallelism — 让 AI 助手学会"该不该并行、并行几个"

Agent Parallelism 是一份给 AI 编码助手（如 CodeBuddy、Claude Code 等）使用的**并行调度技能包**。它帮你的助手回答一个关键问题：**一个任务要不要拆给多个 AI 同时做？拆几个最划算？** 让多 agent 并行真正带来质量提升，而不是更慢、更贵、更乱。

## 它解决什么问题

你一定遇到过这些时刻：

- 「这个仓库几百个文件，扫一遍太慢了，能不能几个 agent 一起查？」
- 「让几个 agent 同时改代码，结果改着改着互相打架，合并一堆冲突。」
- 「派了 8 个 agent，结果比 1 个还慢还贵。」

多派几个 agent 不等于更快更好。事实恰恰相反：**实测中，同一类任务并行后有的提升 80%，有的反而下降 70%**。什么时候该并行、并行几个、怎么防翻车，靠拍脑袋决定很容易翻车——这就是本技能包要解决的问题。

## 适合谁使用

- 经常让 AI 助手处理**大仓库扫描、批量代码审计、多文件分析**的用户
- 希望多件事**同时推进**、提高任务交付速度的用户
- 遇到过 **429 限流**（API 请求过多被暂时拒绝），需要自动调整并发的用户
- 想从零搭建一个**多文件项目**、需要多人（agent）协作又怕乱的用户

> 不适合：简单问答、小改动、单个 agent 就能轻松完成的任务。

## 核心功能与亮点

### 1. 智能判断：该不该并行

接到任务后，助手会先用三个问题快速判断，而不是盲目并行：

1. 子任务能**同时推进**吗？（比如 3 个互不相关的模块分析）
2. 各部分需要**抢同一份持续变化的东西**吗？（比如都在改同一个文件——那别并行）
3. 中间结果能**独立检查**吗？

任一答案不合适，助手会老老实实用单个 agent 完成，并告诉你原因。

**典型场景**：你想让它「同时调研三个技术方案」→ 通过；你想让它「重构整个核心类」→ 它会建议串行。

### 2. 科学决定「并行几个」

派几个 agent 不是越多越好。本技能包内置一套调度模型（来自工业界的扩展性定律 USL），按任务特点算出最优并行数量：

| 任务类型 | 建议并行数 | 这个数哪来的 |
|---|---|---|
| 只读扫描、独立分片（如全仓库搜索） | 8 个，**前提是全活儿够大** | 串行 78~165 秒的小活儿：轮 2 的 **22 个非基线臂没有一个跑赢串行**（0.63~0.83，每片 1~2 个文件）。换一份 36 文件、串行 347 秒的语料（从没参与过拟合）重测：**K=3/4/6/8 全部跑赢**，最高 **2.383×**（§20） |
| 需要写入、有共享状态（各改各的文件，但要合并进同一处登记） | **2 个** | **我们自己真跑出来的**（2026-09-26） |
| 编码主链路 | 短时程孤立任务（改一个功能、修一个 issue）1~2 个；长时程共享产物（从零搭项目）2~4 个且必须隔离工作区 | 经验值，**还没实测**；两档分开是因为实测里它们方向相反：单 issue 那种多 agent 结构**全部小幅下降**，从零建库那种反而 +14.7%~+25.6% |
| 拿不准 | 1 个 | 保守默认 |

**典型场景**：「500 个文件全扫一遍」→ 切成 8 片、每片约 60 个文件，这种情况墙钟**大概率**会快（实测每片 3~5 个文件就有 2.383×；每片 60 个文件是同方向的更远外推，**未实测**）；「扫 12 个文件」→ 别开宽，每片一两个文件的扇出在我们的 25 个臂里**一次都没跑赢串行**。「帮我实现一个新功能」→ 1~2 个足矣，多了反而拖累。

⚠️ 但别把「8~9」当成一个有数可依的加速配方。我们为了量它投了 30 个真实派发的臂（轮 2 的 25 臂：同一份字节冻结的语料、6~7 个并发档、每档 3~4 次、返工计入分母）：N=2 到 N=12 每一档的净加速中位数都落在 **0.63~0.83**，也就是**在这个分片粒度上只读扇出连 1.0 都没过**。更麻烦的是分母本身——同一份语料的串行基线三次测得 78.6 / 86.4 / 165.2 秒，**换一种分母，同一批数据能把建议并行数从 1 翻到 9**。所以那一行仍写作「猜测」（指 σ/κ 那组数），但**盈亏条件已经是量出来的**：见下面两段与参考文档 §18、§20。

**盈亏的机制，以及我们怎么把自己写的判据证伪了一半（§19→§20）**：把每个 agent 的耗时拆成「固定开销 + 边际成本」拟合 40 个去重自报读数，得到**固定开销约 47 秒**（R²=0.376）；扇出的跨度取决于 **K 个耗时里最慢的那个**。于是同样这批人时，**并发效率确实买得到：K=12 时 7.23 倍于串行的 throughput**。我们上一轮据此写下过一个判据——~~"这件事串行本来要 12~14 分钟，开 8~9 路才划算"~~——然后**换了一份从没参与拟合的 36 文件语料、把预测写在计时之前**去测它：串行 347 秒、每片 3~5 个文件时 **N=8 实测 2.383×**，那句话**被证伪**。放掉的那一项是"每片摊薄"，正确形式是 **`串行成本 > (每片摊薄后的成本) × 尾巴`**，也就是问**每片摊完是不是仍比串行便宜**，而不是问"这活够不够大"。同一轮还留下两条更硬的：**（a）我随后写下的"每片要 3~5 个文件"也被证伪**——请求 18 路时平台只让 17 个同时在跑，那 17 个每个只读 2 个文件，跨度 211.7 秒 vs 串行 347.2 秒 ⇒ **1.64×**（这一臂作为"18 路"的证据被装置的并发门拒绝记账）。真正的自变量是**总工作量 ÷ 有效并发 vs 单 worker 固定开销**；**（b）同一个 K=8 两次读数 2.383 与 1.023**（档内散布 80%，比档间差还大），所以下限不该也不能从这些臂里挑"最优 K"。另外 **N=12 那一臂只拿到 0.739×**，不是因为尾巴，而是 12 个 worker 里 1 个被平台连接中断吞掉、重派 99.5 秒照规矩计入分母（没丢的话是 2.47×）——**开宽之前要把"丢一个 worker 的代价"算进去**。并行的确定性收益仍是**上下文隔离与质量**，墙钟要按上面的条件另算。

**那次实测是怎么做的**：一份小代码库，12 个互不相同的小功能 + 1 个大家都要改的登记文件；每档并发都跑完整 12 个功能（N=1 时一个 agent 顺序做完，N=12 时 12 个 agent 各做一个），每个 agent 一个 git worktree 物理隔离，合并后用一套独立参考实现逐点判验收（不采信"我自己测过了"）。结果：**净加速在 2 个就封顶**，3 个开始回落，6 个以后比串行还慢。整个扫描跑了**两轮**，两轮都落在同一个形状上。

**再往后两步：先修尺子，再钉做法（§21→§22）**。核对装置时抓出四个**仪表侧**缺陷：每臂归档两次被当两臂读（样本量虚高一倍，去重后 76 → **40 行 / 8 个臂**）、归档按并发度命名所以跨轮互相覆盖、自测与报告读的不是同一个集合、缺日志被静默跳过。修完 §19 的常数是 **a≈47.0 秒 / b=0.142 秒每行 / R²=0.376**（`ols()` 另用 scipy 独立重算对过位）。然后按 §20 的结论做了更狠的一件事：**把 worker 的做法钉死在简报里**（时钟只有一处权威、每个文件恰好一次读、全片恰好一次机械复核、禁止列目录），并给装置加了三道门——改简报即换 regime（分母不许跨档：同一份 36 文件语料的串行基线因此从 **347.2 秒**变成 **250.652 秒**，−28%）、逐臂记交付并发度 **`cov = Σworker 耗时 ÷ 跨度`**（满并发=cov=K，纯串行=1）、未采集的臂不许被下一臂覆盖。三条可带走的读数：**（a）散布里有一块是编排器自己造的**——派发消息与简报给了两个取钟时刻，6 个 worker 交出双读数，间隔中位 **40.3 秒**（18.1~73.2），与固定开销 47.0 秒同量级；**（b）"开了 N 路"要看交付了几路**：12 支已记 cov 的臂 `cov/N` 只有 **0.35~0.83**，10/12 支不到 0.8，且随 N 恶化（K=12 只剩 0.35）——`concurrency_observed=N` 只证明曲线在某一刻交叠过，一支 K=2 的臂实际只重叠 26 秒（跨度 225.8 秒）照样判过；**（c）投递会掉**：历史 42 支记账臂里 **6 支（14%）至少缺一个 worker**，K=12 档 3/5 支不完整，本轮还出现过"同机另一个会话的任务书被送到我的 worker 手里"。**"净加速 ≈ 交付并发度"这条我猜错了**（`speedup ~ cov` 的 slope −0.08、R² 0.04，n=12），但比值说了另一件事：speedup/cov 中位 0.43（倒数 ≈2.3），**扇出放大的是总人时**，不是单片速度。**κ 仍未辨识**，而且现在知道为什么辨识不了：这条通道在 K≥2 时**从没把请求的并发交齐过**（被拒臂交付 **0.17~0.22**），而**同一简报、同一字节、同一任务**下四次串行基线是 112.953 / 139.603 / 250.652 / 287.568 秒——**分母自己漂 2.55×**。所以「先量你的分母」不是流程洁癖，是目前这条通道唯一站得住的结论。要继续的人，第一步不是派发，是**把同机会话数记进行里**——"先确认这台机器独占"这句我们自己也做不到：第四轮同一时刻 `ps` 只报一个 Qoder 主进程，而主机清单报 **10 个会话里 7 个 running（6 个不是我）**，三次相隔 8 分钟的清单返回逐字节相同的 `updatedAt`。那支 K=6 探针臂在这个条件下实测**投递率 2/6、`cov/N = 0.21`**，四个槽位交回的是**别的会话的任务**（代价是真的：我的 worker 往本仓库写了另一个会话的产物，还改了 `~/.qoder-cn/settings.json` 的权限默认值——均未提交、未回滚，等归属确认）。所以规则从"证明独占"改成"记录 + 过滤"：**只有 `cov/N ≥ 0.8` 的宽档读数才进 κ 拟合**（pin 三轮共 8 次臂损失/被拒，其中 7 次是通道：载荷送空、并发交付不足、以及 worker 执行了**别的会话**的任务书）。而且钉做法并没有让读数变稳：同一个 K=2 两次净加速 1.110 与 **3.242**（档内散布 **98%**）——**主方差住在通道，不在 worker 的轮次**。

**最后这两步把"不可辨识"量成了数（§22 ⑧⑨）**。先给每个 worker 拟合一次成本：同一份 36 文件字节，f0 档 **a=101.84 秒 / R²=0.158**，pin 档 **a≈19~25 秒**（四次档案快照 19.06 / 21.37 / 20.54 / **24.63** ⇒ `a` 是快照不是常数，只能按区间引用；最后那一跳发生在 worker 总数一字不变的时候，改的是**档案里有哪些臂**——未盖派发戳的两条同档臂会共用身份，后一条把前一条从磁盘上吃掉，§22 ⑬），换简报时边际成本基本没动（4.79 对 4.5~4.8 秒/文件，差 ≤6%），**换语料则动**：另一工程上 b≈3.08 秒/文件（低 31.6%）、a≈17.6 秒（只低 7.6%）⇒ `a` 可按简报引用、`b` 必须按语料重新标定——**"单 agent 固定开销"是简报能改的设计变量，压它比调 K 便宜**（也因此旧那句"a≈47.0 秒"必须带上"哪个语料 × 哪档简报"才能引用）。有了 a 就能把任何读数拆成恒等式 `denom × ideal × loss`，那条 **4.285×** 于是拆成 **1.49 × 3.00 × 0.96**：纯分片的天花板 `ideal` 构造上永远小于 N（每条 worker 都要重付一次固定成本），超线性**全部**来自分母抽到慢样本（本轮串行臂比自己那个模型慢 49%），而跨度贴着模型（没尾巴）。再往上一层：造一个**零干扰**的工作负载（σ=κ=0，只用实测的每档残差、含被拒臂的交付并发、以及那三次真实分母），跑技能自带的同一把拟合器——6 个并发度、每档 1 支时 κ̂ 中位 **0.0464**、95% 上沿 **0.1442**，换一种残差建模上沿仍稳。**结论是地板，不是测量**：这条通道上 κ̂ 小于 **0.155** 一律不构成证据（逐档版 seed 7 上沿 0.1442、整袋版**同 reps** 0.1421，而换 seed 会把它推到 0.1506 ⇒ 0.155 是实测带 0.134~0.151 之上留的余量，不是两版取 max）；每档从 1 支加到 5 支，κ̂ 中位不动（0.0464→0.0440）、上沿只从 0.1442 收到 0.1186（多投臂不解决通道），而只把**交付**换成完美，κ̂ 立刻砍半到 0.0251、上沿收到 0.0501（假曲率主要是队列造出来的）。**写入档也补了同一把尺**（`ro_write_cov.py`，从一手时间戳重算）：cov/N = 0.80 / 0.84 / 0.60 / 0.66 / 0.55，按现行门槛只有 1 档过闸；再往上一层，写入档**自己的**零干扰地板量到 κ̂ 上沿 **0.24**（`ro_write_floor.py`：28 个 worker 的 job 散布 + 实测交付 + 实测扇入 N=12 达 111.7 秒），理想化反事实也还有 0.070~0.079 ⇒ §16 那个 κ̂=0.069 **不是写入通道的耦合证据**，K=2 的依据改为「N≥4 实测净加速全部 ≤1」。把分母冻结成一个常数只收到 0.0345／0.1213——**分母以主项污染水平（±43%）、以次项漏进曲率**（拟合里没有 N=1 锚点，整条曲线乘常数会被 σ/κ 部分吸收），所以"逐轮配对分母"仍然必要，但它不是 κ 的救星。要往下走的人，顺序是：独占主机 ⇒ 交付能齐 ⇒ 再谈 ≥6 档 × ≥3 臂。**门槛最后写成了代码**（`ro_fit.py --min-cov 0.8`）：在全部 21 行上，只有两支臂的交付率过闸，而且**都在 N=2**（3.242 与 **1.090**，档中位 2.166、散布 99%），于是拟合器直接回 `fewer than 2 levels -> nothing to fit`——"这条通道辨识不出 κ"不再是我们的判断，是门槛执行后的算术；那两支同并发、同交付、差 3 倍的臂，拆开来看差的只有分母（1.48 对 0.72），正好把上面那句分工在真实臂上复演一遍。

**读这个数要注意**：只有 3 个并发档（1、2、4）复现过，其余各只跑一次；同一档里范围完全相同的两个 agent 耗时能差 3 倍——所以把它当"2 附近"用，别当"精确的 2.09"用。只读那一档我们实测过两轮（25 个臂），读数是「量不出加速、而且分母自己 2.1× 漂」，所以它仍写作猜测。


### 3. 防翻车三件套

并行最容易翻车的三个坑，各有对策：

- **契约先行**：开工前先写清楚「接口约定」（谁负责什么、返回什么格式、边界在哪），避免各干各的、最后对不上。
- **物理隔离**：并发改代码时，每个 agent 在独立的 git worktree（工作目录副本）里干活，互不干扰；测试通过才允许合并。
- **中心化验证**：所有 agent 的产出必须经主 agent 核对后才算完成——实测数据表明，没有这一步，错误会被放大 **17 倍**；有了它，只放大 **4.4 倍**。

**典型场景**：「3 个 agent 从零搭一个项目」→ 基础件先由主线程统一建好，再分片并行，最后统一验收合并。

### 4. 说人话就能触发

无需记忆任何命令。你只要在对话里自然表达，助手就会自动加载这套调度策略：

- 「能不能几个 agent 一起改？」
- 「这个任务能不能拆开同时做？」
- 「加快执行速度」
- 「429 了，降并发」

### 5. 越用越准

每次并行任务结束后，实际耗时会被记录到日志文件（`assets/parallel-log.csv`）。积累几次后，用自带的拟合脚本一跑，调度参数就会替换成你**自己环境里的实测值**，比默认的估算值准得多。

## 常见问题（FAQ）

**Q1：并行一定更快吗？**

不一定。实测中部分任务并行后**耗时反而增加**（比如从 693 秒涨到 1583 秒）。并行真正买到的是**质量与覆盖面**，不是速度。如果诉求是「更快出结果」，本技能会优先优化单 agent 路径，而不是加 agent。

**Q2：派几个 agent 最合适？**

参考上面「核心功能」中的建议表。原则是：只读任务可以大方派；动代码的谨慎派；拿不准就 1 个——串行永远不会因为协调而翻车。另外，如果你的任务单个 agent 已经能做得很好，加 agent 的收益通常归零甚至变负，别为并行而并行。

**Q3：测试全通过了，为什么合并后还是出问题？**

这是并行最阴险的坑，叫**重复实现**：几个 agent 各自独立实现了同一个概念，类名、接口各不相同，测试能过、代码能编译，但代码库里躺着多份互相冲突的实现。本技能的合并环节会专门检查这一点，你人工 review 时也建议留意。

**Q4：遇到 429 限流怎么办？**

直接对助手说「429 了，降并发」。它会用自适应策略（成功就加一点、被限就乘性退避）自动找到当前额度下的最大安全并发数，而不是固定死一个值。

**Q5：怎么知道我的任务适不适合并行？**

直接问助手：「这个任务适合并行吗？」它会用三个判断问题替你分析。你也可以自己快速自检：任务能不能拆成**互不依赖的几块**？拆出来的每块能不能**独立验证**？两者都行，才有并行的价值。

## 故障排查

| 现象 | 可能原因 | 解决办法 |
|---|---|---|
| 助手没有并行，老老实实串行做了 | 任务本身不满足并行条件（这是正确行为） | 确认任务可拆分；确属可并行仍串行，检查 skill 是否正确安装到技能目录 |
| 说「并行」助手没反应 | 表述未触发技能加载 | 明确说「用多个 agent 并行处理」或「派几个子 agent 一起做」 |
| 拟合脚本报错 | Python 版本过旧或路径不对 | 使用 Python 3；确保在项目根目录运行，路径写对 |
| 并行收益不明显 | 默认参数与你的环境不符 | 记录**至少 6 个不同并发度**的实测数据，跑拟合脚本替换默认值 |
| 合并冲突特别多 | 隔离不充分或任务耦合过高 | 确认使用了 git worktree 物理隔离；若任务本身高度耦合，减少并行数 |

## 术语小词典

- **Agent / 子 agent**：AI 助手派出独立干活的「分身」，各自有独立的工作上下文。
- **并发度 K**：同时派出的 agent 数量。
- **契约（contract）**：开工前各方约定好的接口与边界文档，避免各干各的。
- **Git worktree**：git 的多工作目录功能，让每个 agent 在独立的目录副本里改代码，互不干扰。
- **中心化验证**：所有子 agent 的产出由主 agent 统一核对后才算数。
- **429**：API 请求过多时服务端返回的「稍后再试」错误码，即限流。
