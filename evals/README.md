# 评测集（agent-parallelism）

遵循 Agent Skills 规范的评测结构。**未跑过真实 harness**——文件就绪，记分卡为空。

## 三根评测轴（缺一不可）

| 轴 | 文件 | 测什么 |
|---|---|---|
| **触发精度** | `eval_queries.json` | description 是否在该触发时触发、不该触发时休眠 |
| **输出质量（流程遵从）** | `evals.json` | 加载后是否按流程执行（给出 K 及其来源、落盘 contract 等）|
| **输出质量（禁止项遵从）** | `evals.json` | 是否规避明令禁止的做法（软隔离、融合、多数一致当验收）|

只测触发会漏掉静默的输出回归；只测输出会让触发失败不可见。

## 运行方法（每个用例跑两次）

每个用例在**独立上下文**中跑两遍：`with_skill` 与 `without_skill`（基线）。
单会话内连跑会引入跨用例污染，使评分失真。

```
agent-parallelism-workspace/
└── iteration-1/
    ├── eval-Q1/
    │   ├── with_skill/{outputs/, timing.json, grading.json}
    │   └── without_skill/{outputs/, timing.json, grading.json}
    └── benchmark.json
```

**grading.json**（每条断言必须附具体证据，不给"通融分"）：

```json
{
  "assertion_results": [
    { "text": "输出给出一个明确的数值并发度 K", "passed": true,
      "evidence": "原文：'K=4（拟合脚本输出 N_max=4.13）'" },
    { "text": "要求使用 git worktree 建立物理隔离", "passed": false,
      "evidence": "全文只提到按目录分配 owner，未出现 worktree" }
  ],
  "summary": { "passed": 1, "failed": 1, "total": 2, "pass_rate": 0.5 }
}
```

**benchmark.json** 记录每个配置的 `pass_rate` / `time_seconds` / `tokens` 与 `delta`——delta 说明这个 skill 花了多少（时间、token）、买到了什么（通过率）。

## 断言质量标准

- 必须**具体可观察**；"输出质量好" 不算断言
- 避免逐字比对——正确输出换个措辞不该判失败
- 机械可判的断言（文件存在、JSON 合法）优先用脚本判，别用 LLM 判官
- **同模型 LLM-as-judge 有位置偏差、自我偏好、文风偏好**，只能用于整体质量的盲测补充
- 迭代时回头审断言本身：两配置下**恒过**的断言没有区分度，应删；**恒挂**的断言多半写错了

## 收敛判据

结果达预期、人工反馈长期为空、或多轮无显著增益 → 收敛。

## 结构不变量自检（与评测互补）

上方三根轴测的是**行为**，需要真实 harness；`scripts/selfcheck.py` 测的是**结构**，随时可跑：

```bash
python3 scripts/selfcheck.py    # exit 0 才算过
```

覆盖 frontmatter 硬约束、跨文件数字一致、交叉引用可解析、contract/brief schema 一致、
speedup 定义、agentic-drift 检查项是否传导、评测文件结构、常驻记忆与 skill 是否同步等。

**两者不可互相替代**：结构自检全绿 ≠ 行为正确；行为评测通过也不能保证文件之间没有漂移。


## 静态预检结果（2026-09-15）

真实 harness 未跑。做法：把 `eval_queries.json` 的 25 条逐条去撞 `description` + `when_to_use`，标注误触发风险。**这是静态分析，不是实测触发率。**

### 撞出的两个真 bug（已修）

1. **`when_to_use` 与反例 N4 自相矛盾**：原 `when_to_use` 把「并行跑一下这些用例」列为**应触发**，而 N4「用 pytest-xdist 并行跑测试」标为**不应触发**——同一句话在 skill 内部被判成两个相反答案。已改例句并显式写出工具级并行的例外。
2. **Do-NOT-use 漏掉最危险的近失类**：原排除项只有"与并行无关的决策"，但 N3「把这段循环改成并行计算」**明明说了"并行"**，该条款拦不住。已显式加入「并行计算 / 多线程 / 加锁 / 用 xdist 跑测试」的排除。

### 对抗样本对（区分度最高）

**P8「加快执行速度，这个太慢了」（应触发）** vs **N8「这个接口响应时间太慢，优化一下」（不应触发）**
表层措辞几乎相同，区别仅在 P8 指**任务交付速度**、N8 指**程序运行时性能**。任何 description 改动都应优先回归这一对。

### 风险等级

| 等级 | 条目 |
|---|---|
| 高（与触发词直接重叠，靠语义消歧）| N3、N4、N8 |
| 中（部分词面重叠）| N5、N9 |
| 低（无明显词面重叠）| N1、N2、N6、N7、N10 |
| 边界（触发与否不算错）| B1~B5 |

## 实测基线（第 1 轮，2026-09-15）

**方法**：把 `description` + `when_to_use` **原文**交给 **5 个独立子 agent**（各自独立上下文，**看不到答案标注**），每批 5 条 query，正例/反例/边界例**混排**（避免"这批全是正例"的暗示），要求只输出 `{id, load, reason}`。子 agent 被明确禁止使用任何工具、禁止读取文件。

**性质**：这是**描述阅读模拟**，不是真实 harness（harness 观测的是 agent 是否真的调用技能）。比静态文本撞击强，但仍非端到端实测。

| 指标 | 结果 | 目标 |
|---|---|---|
| **Recall** | **10/10 = 100%** | ≥80% ✅ |
| **Precision** | **10/10 = 100%** | ≥80% ✅ |
| **F1** | **100%** | ≥80% ✅ |
| 边界例一致率 | 4/5 | 不计错 |
| 执行质量 | **未测**（需完整 skill 加载）| ≥70% |

**20 条有标注样本全部判定正确。**

最关键的 3 条——P2（未说"并行"的大规模审计）、P7（429 降并发）、P8（最模糊的"加快执行速度"）——**全部正确触发**；反例 N3（并行计算）、N4（xdist 跑测试）、N8（程序运行时性能）**全部正确休眠**。说明 `description` 里的 **"Do NOT use" 条款确实生效**，而非靠运气。

**唯一偏差**：B2「这几个文件一起改了吧」被判 `load=true`。属**边界例**（上方原始标注即写明"触发与否不算错"）。倾向解读：「并发写入」这一触发词与「几个文件一起改」存在词面重叠。

**处置：记录为待观察，不据此改描述。** 为一个边界样本调描述，可能损伤已全对的正例/反例——属对单点过拟合。

**遗留局限（不可忽略）**：
- 子 agent 与主 agent **同族**，无法排除模型自偏好
- 描述与答案标注出自同一方；虽已对答案**盲测**，但**选题**仍有主观性
- 未测"是否真的调用技能"——只有真实 harness 能测

## 输出质量基线（第 1 轮，2026-09-15，配对运行）

**方法**：`with_skill` 臂的子 agent 被要求**读取 `SKILL.md` 并严格按其指引作答**（模拟技能已加载）；`without_skill` 臂不读任何文件、凭自身判断作答。两臂均禁用其他工具、**均不得读取 `evals/` 或 `references/`**（防泄露断言清单）。每臂 5 个用例，分两批以 K=5 串行执行（遵守本项目只读任务 K≤9 的默认上限）。

**判分规则**：断言 PASS = 回复**确立了该要求的行为**；条件性表述（"若要并行则必须…"）且条件明确者计 PASS。证据须可追溯。

| 用例 | with_skill | without_skill | delta |
|---|---|---|---|
| Q1 大规模审计定 K | **5/5** | 0/5 | **+5** |
| Q2 并发写入隔离 | 4/4 | 3/4 | +1 |
| Q3 加快执行速度 | **3/3** | 0/3 | **+3** |
| Q4 结果不一致 | **3/3** | 1/3 | **+2** |
| Q5 反对 16 并行 | 3/4 | 3/4 | 0 |
| **合计** | **18/19 = 94.7%** | **7/19 = 36.8%** | **+11 条 = +57.9pp** |

**结论：技能带来约 58 个百分点的断言通过率提升**，达成执行质量 ≥70% 的目标。

### 技能贡献最大的三处（delta 越大，技能越不可替代）

1. **Q1 +5（满分差）**：基线给不出并发度数值、不做可分解性判定、不提契约落盘。`with_skill` 不仅给出 K=4，还**主动指出"只读分片"那一行不适用**——因为架构审计的研究对象恰是跨模块耦合本身，故 κ 该取 0.05 而非 0.01。说明"按耦合度而非任务数量定 K"这条原则被真正用出来了。
2. **Q3 +3**：基线**把"并行化"列为提速第 1 顺位**（原话"收益通常最大"）——正是技能明令禁止的失败模式。`with_skill` 正确拒绝先加 agent。
3. **Q4 +2**：基线提出「抽取共同主张 → 直接采信为共识」，**正好踩中"多数一致当验收"这条禁令**；`with_skill` 正确区分同题择优 / 异题拼装。

### 断言审计（判分时同步审查断言本身）

| 发现 | 断言 | 处置 |
|---|---|---|
| **断言写反，惩罚了正确行为** | Q5「给出一个具体的、更小的建议 K 值」——`with_skill` 因**要求先说明任务**而未给单一值反而判失败；基线随口给"6 路"却通过 | **已改写**为「给出更小的可行 K（单一数值或明确的范围），而不是只停在「16 不行」」|
| 两臂恒过、区分度低 | Q2 前 3 条；Q5 第 1/3/4 条 | **保留但标注**：作用是防回归（换更弱模型时可能失守），不用于衡量技能增量 |
| 恒挂断言 | 无 | 无需处置 |

### 遗留局限

- **两臂同族模型**，无法排除模型自偏好；且 `with_skill` 臂被显式要求"严格按指引"，比真实场景更服从——**此偏差使 delta 偏高**
- 判分由主 agent 完成（非盲评），但**同一规则对两臂一致适用**
- 只测了"技能被加载后输出是否合规"，未测"是否真的调用技能"
