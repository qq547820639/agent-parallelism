# 触发精度评测集（agent-parallelism）

改动 `SKILL.md` 的 `description` / `when_to_use` 后，用本文件回归测一次。

## 方法

1. 每条 query **跑 3 次**（模型行为非确定），记录触发率
2. 判定阈值 **0.5**：应触发的触发率 > 0.5，不应触发的 < 0.5
3. 边界例触发与否**不算错**，但每次迭代的决策要一致，并记录理由
4. 指标目标：Recall ≥ 80%、Precision ≥ 80%、F1 ≥ 80%、执行质量 ≥ 70%

> 已知偏差：agent 对"自己就能搞定"的简单请求通常不查 skill。因此过于简单的正例可能系统性不触发——这是设计使然，不算 skill 缺陷；但复杂正例必须触发。

## 记分卡

| 指标 | 公式 | 目标 | 基线(v1.2) |
|---|---|---|---|
| Recall | 正例中触发数 / 10 | ≥ 80% | 待测 |
| Precision | 正例触发数 / 总触发数 | ≥ 80% | 待测 |
| F1 | 2PR/(P+R) | ≥ 80% | 待测 |
| 执行质量 | 触发后按清单执行完的比例 / 总触发数 | ≥ 70% | 待测 |

## 输出质量评测 5 条

触发成功 ≠ 输出可用。断言必须**具体可观察**，不能写"输出质量好"。

| # | Prompt | 断言（每条独立判 pass/fail）|
|---|---|---|
| Q1 | 这个仓库 580 个 Python 文件，并行审计一遍 | ①给出明确 K 值；②说明 K 来自脚本输出或参数表，不是估计；③列出可分解性三问的逐条结论；④要求 `contract.md` 落盘 |
| Q2 | 几个 agent 一起改这三张表的字段 | ①要求 `git worktree` **物理**隔离；②**不出现**"各改不同文件"式软隔离作为最终方案；③要求测试门控合并 |
| Q3 | 加快执行速度，这个太慢了 | ①不直接加 agent，先澄清诉求（墙钟时间 vs 吞吐）；②提到"并行不缩短墙钟时间"（CAID 实测）；③若诉求是更快出结果，指向压缩单 agent 路径 |
| Q4 | 这几个子 agent 结果不一致，帮我融合一下 | ①指出应**择优**而非融合；②不把"多数一致"当验收；③要求可复现命令区分优劣 |
| Q5 | 让 16 个 agent 全并行做吧 | ①明确反对；②给出 `N_max=√((1−σ)/κ)` 的计算或参数表对照；③说明超过峰值后吞吐转负 |

**判分**：每条断言 pass 记 1，执行质量 = pass 数 / 总断言数，目标 ≥ 70%。

## 静态预检结果（v1.8，2026-09-09）

未跑真实 harness（需新会话）。做法：把 25 条 query 逐条去撞 `description` + `when_to_use`，标注误触发风险。**这是静态分析，不是实测触发率。**

### 撞出的两个真 bug（已修）

1. **when_to_use 与反例 N4 自相矛盾**：原 `when_to_use` 把「并行跑一下这些用例」列为**应触发**，而反例 N4「用 pytest-xdist 并行跑测试」标为**不应触发**。同一句话在 skill 内部被判成两个相反答案。→ 已改为「这个任务能不能拆开同时做」，并在 `when_to_use` 里显式写出工具级并行的例外。
2. **Do-NOT-use 漏掉最危险的近失类**：原排除项只有"与并行无关的决策"，但 N3「把这段循环改成并行计算」**明明说了"并行"**——该条款排除不掉它。→ 已显式加入「并行计算 / 多线程 / 加锁 / 用 xdist 跑测试」这类**并发编程与工具级并行**的排除。

###  adversarial pair（最难的一对）

**P8「加快执行速度，这个太慢了」（应触发）** vs **N8「这个接口响应时间太慢，优化一下」（不应触发）**

表层措辞几乎相同，区别只在：P8 指**任务交付速度**，N8 指**程序运行时性能**。
→ 已在 description 中加限定：「加快执行速度」仅指**任务交付速度**，不指程序运行时性能。
→ **这一对是评测集里区分度最高的一条**，任何 description 改动都应优先回归它。

### 风险等级

| 等级 | 条目 | 说明 |
|---|---|---|
| 高风险 | N3、N4、N8 | 与 description 中的触发词（并行 / 加快执行速度）直接重叠，靠语义消歧，已加显式排除 |
| 中风险 | N5（多线程加锁）、N9（几个 Pod 在跑）| 部分词面重叠，已加"多线程/加锁"排除 |

## 已知失效模式（改 description 时对照）

- **欠触发**：description 用了术语（"扇出""USL"）而用户说口语（"几个 agent 一起改"）→ 补中英文口语触发词
- **误触发**：description 含过宽动词（"优化""加速""处理"）→ 补 `Do NOT use` 排除项
- **竞争**：其它 skill 的 description 更宽导致抢触发 → 收窄本 skill 边界
